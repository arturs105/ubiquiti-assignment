# Decision log

Append-only. Each entry: date, decision, why, what it costs. The README tradeoffs section is distilled from here at submission time.

## 2026-10-15 Category mapping: tabs filter on `line.id`

_Superseded for Cameras by the 2026-10-19 "Cameras tab" entry; the IoT mapping and the reasoning below stand._

The PDF says `line` is the filter field and promises a mapping it never gives. The Figma file shows the tab bar (All, Cameras, IoT) with only **All** selected; its sample list mixes Protect cameras (G6 Pro Bullet, G6 Entry Pro) with a Protect sensor (USL Environmental), and a second frame shows a filter menu whose options are product lines (UniFi, UniFi LTE, UniFi Protect, UniFi Access). So the design confirms the filter dimension is the line, but defines no Cameras/IoT membership.

Chosen, by `line.id`:

- **All**: every product.
- **Cameras**: `unifi-protect`.
- **IoT**: `unifi-connect`, `unifi-access`, `unifi-led`, `unifi-talk`, `mfi`.

Everything else (network, airmax, edgemax, uisp, amplifi, …) appears only under All.

Why: the spec names the mechanism, so a reviewer grading against it will look for a line mapping, and the Figma sample list already shows a Protect sensor alongside Protect cameras. Against the live feed (698 products on 2026-10-15) Cameras holds 125 products, of which 80 have `deviceType == "camera"` and the rest are NVRs, sensors, chimes, a door lock and other Protect accessories; IoT holds 82.

Considered and rejected: **Cameras = `deviceType == "camera"`**. It makes the tab literally cameras (80 products, all in `unifi-protect`) but silently switches the filter field away from the one the spec names, and splits the Protect ecosystem across tabs. Switching later is a one-line change in the category rules, so this is recorded rather than built.

Costs: the Cameras tab shows some non-camera Protect products. IoT is a judgment call (phones under `unifi-talk` and legacy `mfi` power are arguable) and is stated as such in the README. The mapping is a hard-coded list of line ids; a new line in the feed lands under All until the list is updated.

## 2026-10-15 Caching: store the raw JSON on disk, not SwiftData

Two options were compared. **A:** decode the feed into SwiftData `@Model` objects, populate the store on first launch, serve later launches from the store and upsert from a background fetch. **B:** keep the `Codable` structs as the only model layer, write the raw JSON to disk with a fingerprint next to it, decode the cached file on launch, fetch in the background and replace file and UI only when the fingerprint differs.

Chosen: **B**.

Why:

- The spec asks for "caching (in-memory or disk)" and grades Combine, states and tradeoffs, not persistence depth. One ~700-device blob decodes in milliseconds; a full re-decode on change is not a performance concern.
- One model layer. SwiftData needs a `Codable` DTO plus `@Model` classes plus mapping for nested optional structures (`unifi`, `uisp`, `power`, `compliance`), then a diff-and-delete pass so removed devices do not linger.
- Swift 6 strict concurrency. `@Model` objects are non-`Sendable` references, so crossing from a `ModelActor` to a `@MainActor` view model means passing identifiers and refetching, or projecting to value structs anyway. Value-type models plus a small `actor` store fit without friction.
- Combine stays visible. SwiftData's reactive surface is `@Query` in views, which bypasses the view model. With B, the pipeline is the cache design: cached publisher merged with network publisher, deduplicated on fingerprint.
- Offline launch works from the file alone, so the error state becomes "cached data plus a stale indicator" rather than an empty screen.

Fingerprint: compare the feed's top-level `version` string first; fall back to a content hash only if versions match but bytes differ. Try conditional requests (`If-None-Match` / `If-Modified-Since`) before downloading; if the server honours them, an unchanged feed costs one 304.

Costs: whole-file replacement instead of row-level upserts, so the UI receives a full array swap (fine with `id`-keyed `ForEach` at this size). Filtering stays in memory rather than in predicates. The file lifecycle (atomic temp-file-and-rename write, corrupt-file recovery, schema change between app versions) is ours to handle and test. A reviewer looking for persistence-framework experience will not see it.

## 2026-10-15 `@Observable` view models; Combine for data flow

View models use `@Observable`, not `ObservableObject` + `@Published`. On an iOS 26 target `ObservableObject` is the legacy API and invalidates the whole view on any change. The assignment lists Combine as a bare bullet in a stack list (Swift, SwiftUI, Combine), which reads as "Apple's reactive stack, not RxSwift" rather than "publish view state through Combine". Combine therefore owns the data flow where it earns its place: `dataTaskPublisher` + `decode` + typed errors, the cache-then-network `Merge` described in the caching entry, an image loader that shares in-flight publishers per URL, and a `CombineLatest` filtering pipeline fed by subjects that sinks into view state. Cost: filter inputs exist as both a stored property and a subject, and a reviewer who expected `@Published` state has to read Core to find the Combine. The README tradeoffs section states this reading explicitly.

## 2026-10-15 Model naming: `Product`, decoded from the feed's `devices` array

The feed and issue #1 say "device"; the assignment PDF, the Figma and the coding standards say "product". One model layer (see the caching entry) means one name. Chosen: `Product`, with `deviceType` kept as a field name. Cost: a `CodingKeys` mapping from `devices` to `products` on `Feed`, and a reader who grew up on the feed has to translate once. Glossary in `CONTEXT.md`.

## 2026-10-15 Model depth: curated fields, not full fidelity

The feed has 25 top-level keys and `unifi.network` alone has around 35 optional sub-keys with no fixed schema. Chosen: model only what a screen renders. List and tabs: `id`, `line`, `product.name`, `product.abbrev`, `sku`, `deviceType`, `shortnames`, `images.default`. Details bonus: `unifi.adoptability`, `unifi.protect.fov`, `unifi.protect.suggestedDistance`, `power.baseConsumption`, `minAdoptVersion`, `compliance.modelName`, `isARSupported`. Dropped: `sysids`, `sysid`, `triplets`, `guids`, `videos`, `btle`, `uisp`, `icon`, the rest of `compliance` and `unifi.network`, and `deviceTypes`, which is always a one-element copy of `deviceType`. Cost: adding a detail later means touching the model and its fixture; nothing in the app can show a field the model did not keep.

## 2026-10-15 Line ids and device types stay strings, wrapped

`line.id` becomes a `Line.ID` wrapper struct with named constants for the lines the category rules use. Unknown ids decode without failure. `deviceType` stays a plain `String` until a screen needs it typed. Cost: no exhaustive switch over lines; the category mapping (issue #5) must cover "everything else" explicitly.

## 2026-10-15 Lenient feed decoding: drop and log, never fail the feed

A structurally malformed product (missing `id`, `product` not an object…) is dropped by a private `Lenient<T>` wrapper and `Feed` compact-maps the survivors. Each drop is logged through `os.Logger` with its index; the skipped count is observable in tests. Chosen over silent dropping (hides data bugs) and over a public count on `Feed` (API nothing renders). Placeholder products under line `unknown` are structurally valid and are decoded; hiding them is for the list screen.

## 2026-10-15 Decoding is proven by a trimmed fixture, not the full feed

The live feed is ~795 KB and changes; it does not belong in the repo. Issue #1 adds the test target with a trimmed fixture plus one deliberately malformed product so the lenient path is tested. ## 2026-10-15 `Product.ID` is Foundation's `UUID`; `Line.ID` stays a string wrapper

All 698 feed ids are canonical lowercase UUIDs, so `Product.ID == UUID` costs nothing and gives a `Hashable` navigation route for free. A product whose id is not a UUID is malformed and is dropped by the lenient decoder. Constraint found while checking: the image CDN returns 403 for an uppercase id, and `UUID.uuidString` is uppercase, so the image URL builder must lowercase it. `Line.ID` cannot be a UUID (values like `unifi-protect`) and keeps the wrapper from the earlier entry.

## 2026-10-15 `Product` encodes back into the feed's shape

The models are `Codable` (coding standards), but `Product` flattens nested feed keys with a hand-written decoder, so a synthesised encoder would write flat keys that the decoder cannot read back. Chosen: a hand-written `encode(to:)` that mirrors the feed's nesting, verified by an encode-decode round-trip test over the fixture. Cost: about thirty lines of mirror code, and `minimumAdoptVersion` always encodes under `minAdoptVersion.net` because the model does not remember which of `net` or `protect` it came from. Nothing in the app encodes products today (the cache stores raw feed bytes), so this is correctness insurance, not a feature.

## 2026-10-15 Fixture products are whole live entries, not trimmed to modelled keys

The fixture keeps each of its eleven products exactly as the live feed had them on 2026-10-15, including `sysids`, `triplets`, `compliance` and the rest the model ignores. Why: the decoder's tolerance of keys it does not model is part of what the fixture proves, and a copied entry cannot drift from the real shape the way a hand-trimmed one can. Cost: ~25 KB instead of ~5 KB, and a reader skimming the fixture sees more than the model uses. Malformed products are inline literals in the test file so the broken JSON sits beside its assertion.

## 2026-10-15 Swift names over feed spellings on `Product`

Flattened fields take the name a Swift reader expects, not the feed key: `abbrev` is `abbreviation`, `images.default` is `defaultImageID`, `fov` is `fieldOfView`, `power.baseConsumption` is `baseConsumptionWatts`. The feed spelling survives only in the private coding keys. Cost: a reader comparing the model with the raw JSON has to look at the decoder once; issue #1 wrote `abbrev` and the code deviates from that spelling knowingly.

## 2026-10-15 Optional details are typed strictly

An optional block that is present but has the wrong type (`protect.fov` as a string, `isARSupported` as a number) throws inside the product's decoder, so the whole product is dropped like any other structurally broken entry. Only `adoptability` is lenient within the product, because an unknown enum case is a plausible feed evolution rather than a broken record. Chosen over per-field `try?`, which would silently hide a feed type change behind a nil. Cost: a type change in a detail block removes products from the catalogue until the model catches up, visibly, in the Console log.

## 2026-10-15 Two more details: indoor-only and Wi-Fi generation

Added `compliance.indoorOnly` (20 live products) and `compliance.wifi` (47, values `5e` and `6e`) to `Product` as `isIndoorOnly` and `wifiGeneration`. Why: the details screen is graded on a sensible selection of attributes, and these two are the only dropped fields a buyer reads at a glance; the rest of `compliance` is certification ids, `uisp` is operator tooling, `unifi.network` has no fixed schema, and `sysids`, `triplets`, `guids`, `icon`, `videos` (setup-wizard video asset ids) and the top-level `fcc`, `ic`, `jrf`, `jpa` regulatory ids are internal. `wifiGeneration` stays a string: the feed's spelling is Ubiquiti's own and a screen only displays it. Cost: the fixture grows by one product (an indoor-only Wi-Fi 6E access point), and the model now carries nine optional details.

## 2026-10-15 Networking client is transport only: bytes and validators, no decoding

Issue #2 first said the publisher "downloads the feed and decodes it into `Feed`". Chosen instead: `FeedClient.fetch(validators:)` emits either `unchanged` or the raw `Data` plus the response validators, and the repository in #3 decodes. Why: the store keeps raw bytes (see the caching entry), so a client that emitted `Feed` would force #3 to re-encode, and the encoder drops leniently-skipped products, so the file would not be the bytes that were downloaded. One seam, one shape: the thing written to disk is the thing that came off the wire. The client is feed-specific, not a generic conditional-GET client; one endpoint exists. Cost: `NetworkError` (`network`, `httpStatus`, `invalidResponse`) has no decoding case, so the repository owns a second error type that unions it with `DecodingError`.

## 2026-10-15 Conditional requests are explicit; the feed session bypasses `URLCache`

The live feed answers 304 to both `If-None-Match` and `If-Modified-Since` (checked 2026-10-15), and sends `cache-control: max-age=86400`. With `URLSession`'s default policy the system cache would serve the feed without a network round-trip for 24 hours and a 304 would never reach the app. Chosen: the client sets the headers itself from validators the store persists beside the feed file, uses an `.ephemeral` session with `urlCache = nil`, `requestCachePolicy = .reloadIgnoringLocalCacheData` and `waitsForConnectivity = false`, and surfaces 304 as `unchanged`. Only 200 and 304 are accepted; any other status is `httpStatus(code)`. A 304 without validators sent is treated as `httpStatus(304)`. No retry operator: failure emits once, retry is the user's intent. Rejected: `reloadRevalidatingCacheData`, which hides the unchanged branch and adds a second persistence layer next to the store. The image session in #9 is separate and keeps `URLCache`. Cost: validators are one more thing the store persists and tests cover, and the app never benefits from the system cache for the feed.

## 2026-10-15 Networking tests land with #2, not #4

The test target already exists, so `FeedClient` ships with `URLProtocol`-stubbed tests (success with validators captured, 304 → unchanged, 404 → `httpStatus`, transport failure → `network`, validators sent as headers). The `FeedClient` protocol also gets an in-memory fake for #3 and the view models. #4 keeps store and merge tests.

## 2026-10-15 Networking tests: a `URLProtocol` stub, one URL per test, error codes not errors

The client is tested through the public `fetch(validators:)` on a session whose `protocolClasses` is a stub that replays a scripted status, headers and body per URL and records the request it saw. Chosen over a `URLSession` protocol wrapper (the swift-testing-pro skill's suggestion): the stub exercises the real `dataTaskPublisher`, header handling and the production session configuration, and the client's initialiser already injects the session. Each test registers its script under a unique URL, so Swift Testing's parallel execution needs no serialisation. Equality on `URLError` is not asserted: `URLSession` adds its task to the error's `userInfo`, so tests compare `code`, which is what the display mapper will switch on. `Validators` is `Codable` now rather than in #3 because the store writes it beside the bytes and the type should not change shape once persisted. Cost: a ~60-line stub in the test target, and a stubbed `URLProtocol` cannot prove redirect following or TLS behaviour.

## 2026-10-15 One force unwrap: the feed URL literal

`URLSessionFeedClient.Constants.feedURL` is `URL(string: "https://static.ui.com/fingerprint/ui/public.json")!`. The standard says never force unwrap outside tests; this is the logged exception. Why: Foundation has no non-optional initialiser for a string literal, `URLSessionFeedClientTests.defaultFeedURLIsThePublicUIDBFeed` evaluates the constant and pins it to the URL in `docs/ASSIGNMENT.md` on every test run, so a malformed literal fails the suite rather than the app, and the alternatives (an optional URL threaded through the client, or a `guard` that crashes with a nicer message) make a compile-time constant look like runtime data. Cost: one `!` a reviewer must read past, which the doc comment on the constant explains.

## 2026-10-16 Fakes live in `Core/Fakes/`, in the app target, not behind `#if DEBUG`

`InMemoryFeedClient` moves from `Core/Networking/` to `Core/Fakes/`, where later fakes (`ProductRepository`, `ImageLoader`) join it. Why: the standard says every view carries a `#Preview` per state fed by the in-memory fake, and `#Preview` bodies compile into the app target, so the fakes must too. Considered gating them with `#if DEBUG`: every preview would need the same guard or Release would not build, and the gain is nil because an unreferenced struct with no stored data is dead-stripped anyway. A dedicated folder makes the separation visible by placement instead of by compiler flag. Cost: one more folder under `Core`, and a fake is one file away from the protocol it implements.

## 2026-10-16 SwiftFormat is pinned by `--minversion`, installed by Homebrew

Formatting was declared enforced but nothing ran it: SwiftFormat was not installed and `make lint` covered only the app folder, so PR #13 shipped unlinted. Chosen: Homebrew install, `--minversion 0.63.1` in `.swiftformat` so an older binary refuses to run, `--swiftversion 6.2` to match the Xcode 26 toolchain, and `make format` / `make lint` over both `Ubiquiti Assignment` and `Ubiquiti AssignmentTests`. `make lint` resolves the binary through a Make variable that errors with the install command when it is missing. Rejected: Mint or a SwiftPM build-tool plugin, which pin an exact version but add a manifest and a resolve step to a project with no package dependencies. Cost: `--minversion` is a floor, not an exact pin, so a newer SwiftFormat with a changed default rule can disagree with CI until the floor is raised; CI runs `brew install swiftformat` and so always tests against the newest release.

## 2026-10-16 Four default rules disabled: organizeDeclarations, wrapPropertyBodies, wrapFunctionBodies, swiftTestingTestCaseNames

The first run of the formatter over the tree wanted to move every `init(from:)` above the stored properties and shuffle the `// MARK: - Codable` sections, expand one-line computed properties such as `var id: String { version }` to three lines, and rewrite camelCase test names into backtick strings (`isARSupported` became `AR support`, `WiFi` became `wi fi`). Chosen: disable `organizeDeclarations` (it was opted in earlier without having been run), `wrapPropertyBodies`, its function twin `wrapFunctionBodies` (surfaced by `override class func canInit(with:) -> Bool { true }` in the networking test stub) and `swiftTestingTestCaseNames`, and let the formatter own the rest (imports sorted, trailing commas kept because Swift 6.2 allows them in parameter lists). The one-off reformat is its own commit so a reviewer can skip it. Cost: declaration order and test naming are convention rather than tooling; the coding standards state the `// MARK:` order and the formatter does not check it.

GitHub's `macos-26` image ships Xcode 26.6 and iOS 26.5 simulators, the same as the development machine, so `make test` runs in CI with the deployment target untouched. ## 2026-10-16 Type tokens are semantic text styles; UI Sans is not bundled

Figma (#6) defines five text styles: 16/24 regular and bold in SF Pro Text, 12/16 regular in SF Pro Text, 14/20 regular and bold in UI Sans. Chosen: `.callout`, `.callout.bold()`, `.caption` and `.subheadline` / `.subheadline.bold()` rather than fixed point sizes. SF Pro is the system font, and at the default Dynamic Type size `.callout` is 16pt and `.caption` 12pt, so the first three match Figma and scale with Dynamic Type without extra work. `.body` was the first pick and is 17pt, one point over the design; the token keeps the name `body` because that is the Figma role, not the system style. UI Sans is Ubiquiti's proprietary face, not shipped with iOS and not in the Figma export, so the three tab labels fall back to the system `.subheadline` (15pt against Figma's 14). Line heights (24, 16, 20) are not set as `lineSpacing`, which fights Dynamic Type; the text style owns its leading. Figma's -0.208 tracking on the 16pt styles is not applied: SF Pro already tightens its own tracking per point size, so `.tracking(-0.208)` would stack on top of the system value and stay fixed while the size scales with Dynamic Type. Figma shows the font with no automatic tracking, so the designer's value stands in for what iOS does on its own. Cost: tabs are one point larger than the design and in a different face, which a reviewer comparing against Figma will see.

## 2026-10-17 The app is locked to light mode

Figma defines light values only, and every colour set under `Assets.xcassets/Theme` has a single universal appearance. Without a lock, dark mode switches the system parts (spinner, list chrome, status bar) to their dark variants while the token backgrounds stay #F4F5F6 and #FFFFFF, so the loading spinner turns light grey on light grey. Rejected: inventing dark values for nine colours with no design behind them, and `.preferredColorScheme(.light)` on the root view, which does not reach sheets or alerts presented from UIKit. ## 2026-10-18 User-facing strings are literals backed by a String Catalog

`Localizable.xcstrings` sits in the target with English as the source language and `LOCALIZATION_PREFERS_STRING_CATALOGS` on, so Xcode harvests every `LocalizedStringResource` and SwiftUI string literal into the catalog at build time. Views write the English copy inline (`Button("Retry", …)`, `"Something went wrong"`) rather than through shared constants such as the former `ButtonTitle`; the catalog deduplicates identical literals into one entry, so a constant only guarded against one view being reworded without the other. Cost: the catalog is the single place to see every string, and two views that should keep the same wording are tied only by the shared key, not by the compiler.

## 2026-10-16 Cache-then-network is sequential, not `Merge`

The coding standard and the first caching entry said `Merge` of the cache-read publisher and the network publisher. That was sketched before conditional requests existed. Two facts changed it: the network request needs the validators that sit beside the cached file, so the fetch cannot start until the cache read has finished; and the feed session has `waitsForConnectivity` off, so an offline failure can arrive in milliseconds and a `Merge` would fail the whole stream before the disk read emits, showing the error screen while a good cached feed was about to appear. Chosen: one sequential pipeline. The cache read emits the cached snapshot, `flatMap`s into `fetch(validators:)`, and the result is emitted as current or caught into stale. Rejected: sharing the cache read into two legs that feed a `Merge` (same dependency, hidden), and a truly parallel `Merge` with unconditional downloads (discards the 304 path). Cost: the standard's `Merge` wording is amended, and a reviewer who expected it finds the reason here.

## 2026-10-16 Feed identity is `version` alone; no content hash

The caching entry planned "compare `version` first, fall back to a content hash if versions match but bytes differ". `Feed.id` already claims version is the document's identity, and the two statements contradicted each other. Chosen: trust the API's version. Two responses with the same version are the same feed; bytes are never compared and no hash is computed or stored. When a download carries the version the app already has, the snapshot is emitted as current with the feed already in memory, and the new bytes and validators are still saved so the next request is conditional. Cost: a feed republished with changed content under the same version is not noticed until its version changes. **README**: the tradeoffs section must say that hashing the whole JSON was considered and rejected in favour of the API-provided version.

## 2026-10-16 One `FeedRepository`, no separate store protocol

Issue #3 and the coding standard planned an `actor FeedStore` behind a generic `Cache` protocol plus a repository composing it with the client. Chosen: one type. `FeedRepository` is a protocol with one requirement, `feed() -> AnyPublisher<FeedSnapshot, FeedError>`; `CachedFeedRepository` is an `actor` that holds the in-memory copy, reads and writes the two cache files, decodes, and builds the pipeline; `InMemoryFeedRepository` in `Core/Fakes/` serves view models and previews. Why: a store with `load` / `save` / `clear` has an interface as large as its implementation, exists only to be faked, and the repository's fake exists either way. Testing the pipeline through a temporary directory per test is fast and tests the behaviour a user sees. Cost: pipeline tests touch the filesystem, and one actor has three reasons to change (file layout, decoding, orchestration), kept readable by splitting the disk code into an extension file. The standard's `Cache` line is amended; the fakes entry above names the repository fake `ProductRepository`, which is now `InMemoryFeedRepository`.

## 2026-10-16 What is on disk and how a broken cache recovers

Two files under `Library/Caches/Feed/`: `feed.json`, the downloaded bytes verbatim, and `validators.json`, the `Validators` the server sent with them. Writes go to a temporary file then rename. The in-memory copy is the last loaded or saved pair, so a re-subscription (pull to refresh) skips the disk read. Rules: validators missing, feed present → load the feed, fetch unconditionally. Feed missing, unreadable or not decodable with the current model (a schema change between app versions) → delete both files, treat as no cache, fetch unconditionally; validators are never sent when there is nothing a 304 could confirm. A cached feed that decodes to zero products is a valid, empty cache. Fresh bytes that fail to decode while a cached feed exists are not written; the cached feed is shown as stale with the decoding error. A failed write is logged and never surfaced: the user has the feed, caching it is not their problem.

## 2026-10-16 The repository emits snapshots; stale is a value, not an inferred failure

`FeedSnapshot` is the `Feed` plus a `freshness`: `cached` while the refresh runs, `current` once the server answered with a new feed or with unchanged, `stale(FeedError)` when the refresh failed and the cached feed stands. The publisher fails only when there is nothing to show. Rejected: emitting bare `Feed` values and letting the view model infer "stale" from a failure that follows a value; the stale indicator (#6) is a graded state and deserves a name. `FeedError` has two cases, `network(NetworkError)` and `decoding(String)`, the string being the decoding error's description so the enum stays `Equatable` for tests and for the display mapper. Glossary: Snapshot, Stale, Cached feed in `CONTEXT.md`.

## 2026-10-16 Caching tests land with #3, not #4

As with #2: round-trip through the files, the four recovery rules, cache-before-network order, stale on offline, current on unchanged, same-version download, and the fake replaying what it was given. #4 keeps whatever is unclaimed when it is reached.

## 2026-10-16 `CachedFeedRepository` is a `final class` behind a `Mutex`, not an `actor`

Issue #3 and the entries above planned an `actor` whose async calls were bridged into Combine with `Deferred` + `Future`. The compiler refused it: `Future.Promise` is a plain non-`Sendable` closure, so handing it to the `Task` that awaits the actor is a `sending` violation under Swift 6, and the only ways through are `nonisolated(unsafe)` or an `@unchecked Sendable` wrapper, which the standard bans unless unavoidable. It is avoidable. Chosen: the in-memory copy lives in a `Mutex` inside a `Sendable` final class, every step of the pipeline is synchronous, and the chain is one `Deferred` with no bridge: read the cache, `prepend` the cached snapshot, `flatMap` the fetch into decode-and-remember, `catch` into stale. The disk write still happens after the snapshot is emitted, as an `append`ed `Deferred` that writes and completes empty, so the screen never waits on disk and a test's completion means the files are there. `subscribe(on:)` a private serial queue keeps the disk read off the subscriber's thread; that is the one scheduler in Core and it is about where work starts, not where values are delivered. The write appended after the `current` snapshot subscribes on the same serial queue, so two overlapping refreshes save their pairs one after the other and `feed.json` and `validators.json` never come from different downloads. Cost: a reviewer who read the earlier entries expecting an actor finds a `Mutex` and this entry; the class keeps the standing declaration order (stored properties, `init`, protocol API, private helpers) by hand, as `organizeDeclarations` is disabled. One branch the spec did not name: unchanged with no cached feed. The real client cannot produce it (unchanged only answers a conditional request, and validators exist only beside a cached feed), so the repository fails with `network(httpStatus(304))`, the same error the client reports for a 304 to an unconditional request, rather than inventing a snapshot from nothing. A test pins it.

## 2026-10-16 Tests watch the client's validators through a recording wrapper in test support

The recovery rules are observable only through what the repository asks the client for: `Validators.empty` after a missing feed file, the stored validators after a good one. `InMemoryFeedClient` ignores validators by design, and giving the fake a recorder would put test state into the app target. Chosen: `RecordingFeedClient` in `Ubiquiti AssignmentTests/Support/`, a `Sendable` wrapper around the in-memory fake that appends each request's validators to a `Mutex`-held array. Rejected: asserting on log output or on private state. Cost: one more ~25-line test helper next to `StubURLProtocol`.

## 2026-10-17 Core is async/await; `CachedFeedRepository` is an `actor` with two async methods; Combine moves to the view models

The entry above bought a Combine-shaped repository with a `Mutex` and a private serial `DispatchQueue`, because the actor planned in #3 could not be bridged into a publisher under Swift 6 without unchecked code. That cost was paid to keep Combine in Core, and Combine is in Core only because the standards read the assignment's bare "Combine" bullet as "the data flow must be publishers". Re-read: the bullet names Apple's reactive stack, and the place a reactive pipeline earns its keep is derived view state (tab plus products into a filtered list), not a request that produces one value. Chosen: Core is async/await and imports no Combine. `FeedClient.fetch(validators:)` is `async throws(NetworkError)` on `URLSession.data(for:)`; the one untyped error that call can throw is wrapped as `URLError(.unknown)` with the original underneath, so the failure type stays typed. `FeedRepository` has two requirements, `cachedSnapshot() async -> FeedSnapshot?` and `refresh() async throws(FeedError) -> FeedSnapshot`, and `CachedFeedRepository` is a plain `actor`: memory is actor state, disk is read and written on the actor, the network call is the only suspension point and memory is read again after it, so two overlapping refreshes integrate and save one after the other and memory and disk never disagree (they could, briefly, with the queue). The disk write now completes before `refresh()` returns: milliseconds on the actor, with the cached snapshot already on screen, and a returned snapshot is a saved one, which the tests rely on. Rejected: one `feed()` returning `AsyncThrowingStream<FeedSnapshot, any Error>`, which keeps the single requirement but drops the typed failure the rest of the layer insists on; and a hand-written `AsyncSequence` with `Failure == FeedError`, which is ceremony for a sequence of at most two elements. Two awaited calls in order is what the view model would have written against the stream anyway. Combine now lives in the view models: subjects for inputs, `CombineLatest` for the filtered list, and the image loader shares in-flight `Task`s, not publishers. Cost: a reviewer grading Combine finds it in `Features/`, not `Core/`, and the README tradeoffs section must say so and point here; the three caching entries above and #3 describe a publisher of snapshots that no longer exists, and this entry is the correction; the standards' Combine section is rewritten as "Concurrency and Combine"; `Publisher.emissions()` in test support becomes `FeedRepository.load()`, which runs the two calls as the view model will; `InMemoryFeedRepository` takes a cached feed and one refresh outcome instead of a list of snapshots.

## 2026-10-17 The repository holds no feed in memory; `refresh()` reports an outcome, not a snapshot

The entry above kept an in-memory copy of the cached pair as actor state (`Memory`: unread, loaded nothing, loaded a pair), because `refresh()` returned a whole `FeedSnapshot` in every outcome and owned the stale fallback: a 304 has no body, a failed refresh had to hand back the held feed, and a same-version download had to return the held value. The copy existed to serve that contract, not the user: the initial load reads disk regardless, and on pull to refresh the view model already holds what is on screen. Chosen: the leaner contract. `FeedRepository` is `cachedFeed() async -> Feed?` and `refresh() async throws(FeedError) -> FeedRefresh`, where `FeedRefresh` is `unchanged` or `updated(Feed)`; a failed refresh throws and the caller keeps what it shows. `FeedSnapshot` and its `Freshness` are deleted; cached, current and stale become view-model state, where the screen already decides what to show. `CachedFeedRepository` has no stored state beyond `client` and `directory`: `cachedFeed()` reads the pair, `refresh()` reads it again for the validators, fetches, decodes, saves, returns. The read-before-fetch stays a full read, feed included, because validators are only sent beside a feed that decodes and reading the pair is what proves that: one ~700-device decode per pull, milliseconds on the actor, which the 2026-10-15 caching entry already accepted as not a performance concern. Two things move to the view model: whether a same-version download replaces the list (the repository holds nothing to compare against; `Feed` is `Equatable` and the Combine pipeline can `removeDuplicates()`), and the stale state (`FeedError` kept beside the feed on screen). Gained: a repository whose every call starts from disk cannot drift from what is saved, a purged `Library/Caches` is noticed on the next load instead of masked for the rest of the session, and `remember`, `staleOrThrow` and the `Memory` enum go. Cost: the view model owns freshness and must be tested for it when it lands; three entries above (2026-10-16 ×2, 2026-10-17) describe snapshots that no longer exist, and this entry is the correction. Glossary: Snapshot is replaced by Refresh outcome in `CONTEXT.md`; Stale is reworded as view-model state. `FeedRepository.load()` in test support now returns `FeedLoad` (the cached feed plus the refresh result) and `InMemoryFeedRepository` takes a `FeedRefresh` or an error, with or without a cached feed.

## 2026-10-17 The repository streams updates: `updates()` is an `AsyncStream<Feed>` beside the two calls

The two entries above left `FeedRepository` pull-only: the view model calls `cachedFeed()` then `refresh()` and applies what comes back. That works for one screen with one trigger, and stops working the moment a second source of change exists (a push notification, a background refresh, a second screen pulling): every reader would have to be told by every writer. The repository is the single source of truth for the feed, so readers should subscribe to it once and writers should only have to call `refresh()`. Chosen: a third requirement, `updates() async -> AsyncStream<Feed>`, yielding every feed a refresh saves, from whichever caller triggered it, right after the disk write; never the cached feed (`cachedFeed()` already hands it out) and never a failure (those stay typed on `refresh()`, which is why `AsyncThrowingStream` was rejected on 2026-10-17 and is not revisited). `CachedFeedRepository` stays an `actor` and keeps one continuation per subscriber, dropped on termination; that is the only state beyond its two files, and it is a list of listeners, not a copy of the feed, so "every call starts from disk" still holds. Buffering is newest-one: a subscriber mid-render when two downloads land only wants the last. `refresh()` still returns its outcome so the caller that asked can end its spinner and clear stale without waiting on the stream. Correction to the 2026-10-17 async entry: it says the actor "could not be bridged into a publisher under Swift 6 without unchecked code", which overstates it. A Combine publisher from an actor needs exactly one `@unchecked Sendable` box around a subject, because Combine's subjects are not `Sendable` in the iOS 26 SDK; that is a choice we decline, not an impossibility. An `AsyncStream` needs no unchecked code at all, which is why it is the shape here, and Combine stays in the view model as the standards say: one task in `load()` iterates the stream and sends into the products subject, and from there the `CombineLatest` pipeline is unchanged. Cost: `InMemoryFeedRepository` becomes an `actor` too, so it can hold subscribers and offer `publish(_:)` for view model tests that need an update nobody on screen asked for; `RecordingFeedClient` in test support replays a sequence of outcomes so one test can refresh twice; the standards' "no state beyond its two files" is reworded. Glossary: Update is added to `CONTEXT.md`.

## 2026-10-18 One stream, not two calls: `feed()` opens with the cached feed and continues with every update

The entry above left the read side in two places: `cachedFeed()` for what disk holds now and `updates()` for what later refreshes save, with the comment on `updates()` saying "never the cached feed" to keep them apart. That split pushed a choreography onto every consumer: read the cache, subscribe, then refresh, with the order of the last two a correctness rule the types did not enforce (subscribe late and the first download is missed) and no catch-up for a subscriber that arrived after a refresh (a second screen had to call `cachedFeed()` itself). Reversed: the two reads collapse into one, `feed() async -> AsyncStream<Feed?>`, whose first element is the cached feed or `nil` and whose later elements are every feed any refresh saves. `cachedFeed()` and `updates()` are gone; `refresh()` stays as the one write, still returning its outcome so the caller can end a spinner or clear stale without reading the stream. This is the shape of every "store exposes a stream of state" design (a `CurrentValueSubject`, `@Published` on a store, Firestore and Realm observation) and reads as one query and one command. The element is `Feed?` rather than `Feed` so "no cache yet" is expressible: a view model that sees `nil` shows loading instead of waiting for an element that may never come. `nil` is only ever the opening element, which the doc comment states. Inside `CachedFeedRepository` the disk read and the subscriber registration happen in one actor turn, so no refresh can save a feed between them: a subscriber sees what disk held at that moment, then every change, with no gap and no duplicate. Buffering stays newest-one, and the opening element is subject to it like any other: a subscriber that only starts reading after two downloads gets the second download, not the stale cache, which is the right outcome and is pinned by a test. `InMemoryFeedRepository` now keeps the last published feed as its cached one, as production does through disk, so a late subscriber of the fake starts from it too. The standards' cache-then-network bullet and the glossary's Update entry are reworded; the "never the cached feed" rationale of 2026-10-17 is withdrawn, not the stream itself.

## 2026-10-18 `refresh()` reads the cached feed's header, not the whole feed

Issue #3 US8 asks that the cached file is decoded in one place so the lenient decoder's drops are logged once per load. The single-stream shape broke it: `feed()` decoded the cached file, then `refresh()` decoded it again to prove its validators may be sent, so every "Dropped product" and "Loaded cached feed" line was logged twice per load. Chosen: `refresh()` decodes only the top level (a string `version`, and `devices` being an array) through a private `FeedHeader`. `Feed` decodes products leniently and fails only on that top level, so the header decodes exactly when `Feed` does and the same recovery rules apply; tests pin the equivalence through `refresh()` alone. The 2026-10-17 entry's "the read-before-fetch stays a full read, feed included" is withdrawn: still one JSON parse per refresh, but no product decoding and no duplicated log lines. The header also hands `refresh()` the cached version, which the same-version log line needs. Rejected: a flag on the decoder to silence drop logging (the second decode stays, and a model type grows a logging switch), and remembering the validators in memory (the 2026-10-17 entry dropped in-memory state so a purged cache is noticed). Cost: a second decodable shape of the feed's top level that must change with `Feed`'s, kept beside the disk code and pinned by tests.

## 2026-10-18 The cache write removes the old validators before replacing the feed

Each file is written atomically, but the pair is two renames, so the earlier claim that "a crash mid-write leaves the previous pair intact" did not hold: a crash or a throw between the renames left the new `feed.json` beside the old `validators.json`, and the next request would send validators that do not belong to the bytes on disk, so a 304 could confirm a feed the server never sent with them. Chosen: encode the validators first, then delete `validators.json`, write `feed.json`, write `validators.json`. Every intermediate state is a valid cache: a feed without validators loads and is fetched unconditionally (the 2026-10-16 recovery rules). Rejected: a directory swap (write both into a temporary directory and rename it over the old one), which is one atomic step but needs a replace-directory dance `FileManager` only offers through `replaceItemAt`, for a window of microseconds. Cost: a crash in that window costs one unconditional download on the next launch.

## 2026-10-18 A missing feed file is no cache, not a recovery

The recovery rules treated every failed read of `feed.json` as a broken cache, so an ordinary first launch logged a `.notice` "removing the cache files" from `feed()` and again from `refresh()`. Chosen: a missing file (`CocoaError.fileReadNoSuchFile`) is plain no cache, logged at `.info`, and only an orphaned `validators.json` beside it is removed, as before. A file that exists but cannot be read, or does not decode, still deletes both. Considered and not taken: sparing unreadable files too, for transient errors such as data protection before first unlock. The cache sits in `Library/Caches` with the default protection class, which is readable after first unlock, and the app reads it only when a screen or refresh runs, so the case is a background refresh before first unlock; deleting there costs one unconditional download, while keeping an unreadable file needs a rule for when to give up on it.

## 2026-10-18 Overlapping refreshes are not coalesced

Two `refresh()` calls that overlap both read the same validators and both fetch, because the actor gives up isolation while the network call is in flight. Each response is then applied whole, one after the other, so the two files never mix, but in completion order: if the server changed the feed between the two requests and the older response lands last, it overwrites the newer feed on disk and is the last element subscribers see; with no cache, both calls download the full feed. Considered: sharing one in-flight `Task` in the actor, as the image loader does per URL, which fixes both. Not taken in #3: the only caller today is one screen's load and pull to refresh, where the view model already cancels the refresh in flight before starting another (see the standards), so overlap needs two screens or a background refresh, neither of which exists yet; and a shared task brings cancellation rules of its own (one caller cancelling must not cancel the other's fetch). Cost: revisit when a second refresh trigger lands; the fix is local to `refresh()`.

## 2026-10-18 `ImageLoader` takes a product and a size, returns `UIImage`, throws `ImageError`

## 2026-10-18 `ImageError.invalidImage` carries the underlying error's description

## 2026-10-18 The list view model: three subjects in, state and stale error out

Inputs are three `CurrentValueSubject`s: the feed (`Feed?`, fed by the task iterating `feed()`, deduplicated by `version` per the corrections entry), whether a refresh is in flight, and how the last refresh ended (`FeedError?`, cleared on `unchanged` or `updated`). `state` is a `CombineLatest3` over them: no feed and no failure is `loading`; no feed and a failure is `failed`, except while a retry runs, which reads as `loading` again so Retry visibly does something; a feed with rows is `loaded`, and a feed without rows (none, or placeholders only) is `empty` unless the last refresh failed, when it is `failed` like no feed at all: an empty screen over a failed refresh would claim the catalogue is empty and give no sign the server was never reached, and the banner's "Showing saved products" copy has no products to refer to. `staleError` is a `CombineLatest` of feed and failure: the failure when rows are on screen, `nil` otherwise, so the banner and the error screen never show at once. `isRefreshing` mirrors its subject so the banner can swap Retry for a spinner. Nothing else is derived by hand. The category subject #10 adds becomes a fourth input to the state pipeline and the filter moves into its `map`. Intents: `load()` subscribes once and starts the first refresh; `refresh() async` is for `.refreshable`, which needs to await the server; `retry()` starts one without waiting, for the two Retry buttons. A refresh asked for while another is in flight joins it: the intent returns the running task and `refresh()` awaits that, so a pull during `load()`'s first refresh ends its spinner when the server answers. A first draft cancelled and restarted instead, which asked the server twice for the same thing and ended the pull's spinner at once while the newer refresh was still running. The standard's "a repeated intent cancels the one in flight" is amended to name its two exceptions: `load()`, which subscribes once and ignores a repeat, and a refresh, which joins. This corrects the 2026-10-18 "Overlapping refreshes are not coalesced" entry, which rests on the view model cancelling the refresh in flight before starting another: the list screen now coalesces its own refreshes by joining, so an overlap in the repository still needs a second caller, and that entry's decision and cost stand. Both tasks capture `self` weakly and are cancelled in an `isolated deinit`, so a dropped view model drops its subscription and a refresh in flight cannot keep it alive; the tasks and the cancellables are `@ObservationIgnored`, since no view reads them. Cost: the inputs exist as subjects, not as the stored properties a reader would expect, and the view model has three sinks where one state struct would do; the standards' "the pipeline is written out as publishers" is the reason. Joining also means a pull cannot escape a stalled request: its spinner lasts until the session's default 60-second request timeout fires, where cancel-and-restart let the user try again at once. Accepted, because a stalled request is rare and a restart would likely stall on the same network; a shorter timeout on the feed session is the fix if it shows up.

## 2026-10-18 View model tests poll for the state they expect

The feed stream is iterated by the view model's own task, so a state that follows a refresh lands a hop after `refresh()` returns, and an update pushed through the fake's `publish(_:)` lands whenever that task runs. Chosen: `settles(_:at:within:)` in test support, which yields on the main actor until `state` equals the expected value or two seconds pass, so a test states the end state and nothing about scheduling. An end state that spans more than `state` (the new rows and the end of the refresh, which reach the view model through two tasks in either order) goes through `settles(_:within:until:)` with a predicate over the view model, never a `settles` on `state` followed by a plain `#expect` on the rest. Rejected: `Observations` over `state`, whose `@Sendable` closure cannot read a main-actor property under default isolation without ceremony, and making `load()` async, which would tie the subscription's lifetime to the caller. Cost: a failing test takes two seconds to say so.

## 2026-10-18 `settles` sleeps between checks and waits up to ten seconds

CI failed the three view model tests that call `load()` without awaiting `refresh()`: `loadRendersTheCachedFeedBeforeTheRefreshAnswers`, `loadAloneReplacesTheCachedFeedWithTheRefreshedOne` and `loadingTwiceRefreshesOnce`. Locally they pass fifteen runs in a row. Those are the only tests that poll while the feed task is still hopping through the repository actor; every other test suspends on `refresh()` first, and by the time it polls the cached feed has landed. The previous entry's `Task.yield()` re-enqueues the polling task at once, so three such tests in parallel keep the main thread busy and, on a runner with few cores and several simulator clones, starve the actor hop past the two-second deadline. Chosen: `settles` sleeps ten milliseconds between checks, which leaves the main thread idle in between, and gives up after ten seconds rather than two, since a stalled runner was observed holding a test for over ten seconds and a passing test never waits the deadline out. Rejected: raising the deadline alone, which leaves the busy loop that causes the starvation, and `withObservationTracking` over `state`, which needs a continuation per field the predicate reads and buys nothing over a sleeping poll in a test. Cost: a failing test takes ten seconds to say so, within the suite's one-minute limit.
